13-1. Renderer-neutral Render Specification 설계 및 컴파일러 구현

목표
12단계까지 완성된 Production Plan + Production Blocks + Speech Assets + Generated Assets + manifest를 입력으로 받아,
특정 렌더링 기술(Remotion/HTML/CSS/SVG/Canvas/FFmpeg/영상 생성 AI)에 종속되지 않는
"Render Specification"을 생성한다.

이번 단계의 핵심은 영상을 실제로 렌더링하는 것이 아니다.

13-1에서는:

Production Plan
→ Rendering Readiness Gate 확인
→ Render Specification

까지만 구현한다.

Remotion 프로젝트 생성, HTML 영상 렌더링, FFmpeg 영상 합성, AI 영상 생성, 최종 MP4 출력은 이번 단계에서 하지 않는다.


==================================================
0. 절대 원칙
==================================================

기존 05~12-9 파이프라인을 깨뜨리지 않는다.

특히 다음 데이터는 수정하지 않는다.

- video_scripts
- video_directions
- block_directions
- production_plans
- production_blocks
- speech_assets
- generated_assets의 기존 생성/리뷰 결과
- 기존 WAV
- PAUSE 3000ms
- viewer_action
- Human Review 상태
- Production Plan의 speech text

13단계는 기존 결과를 소비하는 downstream 단계다.

기존 데이터를 13단계 요구에 맞추기 위해 고치지 말 것.


==================================================
1. 12-9 Renderer Entry Contract를 그대로 사용
==================================================

13 Renderer의 진입 조건은 반드시 12-9에서 확정한 canonical persistent readiness만 사용한다.

허용:

compute_persistent_rendering_readiness(...)

또는 canonical manifest의:

ready_for_rendering

persistent_rendering_readiness

금지:

run_local_ready_for_rendering

ready_for_rendering_gate()

현재 CLI 실행 mode(DRY_RUN/SAMPLE/FULL)를 Renderer 진입 판단에 사용하는 것

Plan 7 현재 기대 상태:

ready_for_rendering = YES
FULL EXECUTED = YES
Generation Units = 51/51
GENERATE = 0
BLOCKED = 0
Rendering Blockers = NONE

Renderer Entry Gate가 NO이면 Render Specification을 생성하지 말고,
정확한 blocker를 보고할 것.


==================================================
2. 이번 단계의 핵심 설계 원칙
==================================================

Render Specification은 Renderer-neutral이어야 한다.

즉 아래와 같은 구현 세부사항을 Render Specification에 넣지 않는다.

금지 예:

React component
Remotion Sequence
Remotion AbsoluteFill
CSS class name
HTML div
Canvas API call
FFmpeg filter_complex
MoviePy object
Motion Canvas Node
특정 AI 영상 API payload

Render Specification에는 "무엇을 보여주고 언제 보여줄지"만 기록한다.

"어떻게 렌더링할지"는 후속 Renderer Adapter가 결정한다.


==================================================
3. 장기 Architecture를 고려할 것
==================================================

향후 구조는 다음과 같다.

05~12
Content Pipeline
    ↓
13-1 Render Specification
    ↓
13-2 Timeline Compiler
    ↓
13-3 Scene / Layout Model
    ↓
13-4 Visual Component System
    ↓
13-5 Renderer Adapter
    ↓
13-6 Preview Renderer
    ↓
13-7 Final Video Renderer


그리고 Renderer Adapter 아래에는 향후 여러 구현이 올 수 있다.

Render Specification
    ↓
Visual Strategy / Renderer Adapter
    ├─ Remotion
    ├─ HTML/CSS/SVG
    ├─ Canvas
    ├─ Motion Canvas
    ├─ FFmpeg
    └─ AI-generated visual/video asset

따라서 13-1의 데이터 구조가 특정 도구 하나를 전제로 해서는 안 된다.


==================================================
4. Render Specification의 역할
==================================================

Render Specification은 다음 질문에 답해야 한다.

1. 어떤 Production Plan을 렌더링하는가?
2. 영상의 논리적 장면은 무엇인가?
3. 각 장면의 교육적/콘텐츠적 목적은 무엇인가?
4. 어떤 Speech/Audio Asset을 사용하는가?
5. 어떤 텍스트를 보여줘야 하는가?
6. 어떤 단어/음소/정답을 강조해야 하는가?
7. 어떤 viewer interaction이 필요한가?
8. 어떤 PAUSE를 보존해야 하는가?
9. 정답은 언제 공개할 수 있는가?
10. 어떤 visual intent를 가져야 하는가?

단,

정확한 frame/start/end 계산은 13-2 Timeline Compiler의 책임이다.

13-1에서 임의의 타이밍을 발명하지 않는다.


==================================================
5. 새 모듈
==================================================

가능하면 신규 핵심 모듈:

research/render_spec.py

를 만든다.

불필요하게 여러 파일로 쪼개지 말 것.

필요한 경우 DB schema는 research/db.py에 최소 추가 가능.

CLI는 기존 research.cli 패턴을 따른다.

예상 CLI:

python -m research.cli render-spec --plan-id 7

단 기존 CLI 명령의 동작/시그니처를 변경하지 않는다.


==================================================
6. Render Specification 기본 구조
==================================================

아래는 개념 예시이며 그대로 하드코딩하지 않는다.

{
  "spec_version": "13.1",

  "production_plan_id": 7,

  "rendering_readiness": {
    "ready": true,
    "source": "persistent"
  },

  "video": {
    "format": "EDUCATION",
    "orientation": null,
    "width": null,
    "height": null,
    "fps": null
  },

  "scenes": [...]
}

주의:

width/height/fps가 upstream 데이터에 없다면 임의로 1920x1080/30fps를 넣지 말 것.

13-1에서 결정할 근거가 없으면 null/UNRESOLVED 또는 명시적인 default policy 후보로 남긴다.

사실과 정책을 구분할 것.


==================================================
7. Scene 모델
==================================================

각 scene은 최소 다음 lineage를 가져야 한다.

scene_id
production_plan_id
content_block_id
source_speech_asset_ids
generation_unit_ids

그리고 의미 정보:

scene_role
visual_intent
content_intent
viewer_action
answer_reveal_policy
text_elements
audio_elements
pause_requirements
emphasis_targets

필요하면 추가 필드를 설계해도 되지만
실제 downstream 필요성이 설명되지 않는 필드는 추가하지 않는다.


==================================================
8. Scene Role taxonomy
==================================================

현재 Production Plan의 실제 데이터에서 scene 역할을 도출한다.

예상 가능한 의미 예:

OPENING
QUESTION
EXPLANATION
WORD_DEMO
PHONEME_DEMO
BLENDING
PRACTICE
MINI_SUCCESS
ANSWER_REVEAL
RECAP
RESOLUTION
ENDING

하지만 이 목록을 무조건 강제하지 말고
현재 production_blocks / production_intent / timeline 데이터를 먼저 조사한다.

실제 데이터에 존재하는 의미를 보존하면서
최소 taxonomy를 설계한다.

UNKNOWN으로 조용히 뭉개지 말 것.

분류 불가능하면 UNRESOLVED와 근거를 남길 것.


==================================================
9. Visual Intent
==================================================

Scene Role과 Visual Intent를 분리한다.

예:

scene_role = PHONEME_DEMO
visual_intent = FOCUS_PHONEME

scene_role = MINI_SUCCESS
visual_intent = QUESTION_THEN_REVEAL

scene_role = EXPLANATION
visual_intent = SUPPORT_NARRATION

Visual Intent는 "디자인"이 아니다.

예를 들어:

검정 배경
초록 글자
폰트 크기 72
왼쪽에서 슬라이드

같은 것은 아직 정의하지 않는다.

대신:

FOCUS_WORD
FOCUS_PHONEME
BUILD_SEQUENCE
QUESTION_THEN_REVEAL
COMPARE
SUPPORT_NARRATION
RECAP

같은 의미 수준으로 표현한다.


==================================================
10. Visual Strategy 확장 지점
==================================================

향후 같은 scene이라도 다음 방식으로 시각화할 수 있어야 한다.

CODE_GENERATED
AI_GENERATED
SOURCE_CLIP
STATIC_IMAGE
MOTION_GRAPHIC
TEXT_ONLY
HYBRID

하지만 13-1에서는 실제 전략을 무리하게 선택하지 않는다.

필요하다면:

visual_source_requirement
visual_generation_candidates

같은 형태로 "가능한 방식"만 표현한다.

특히 AI 영상 생성 서비스를 Renderer의 대체재로 설계하지 말고,
Visual Asset Provider 중 하나로 붙일 수 있는 구조를 고려한다.

예:

scene
 ↓
visual requirement
 ↓
CODE / SVG / IMAGE_AI / VIDEO_AI / SOURCE_CLIP
 ↓
Renderer

최종 타임라인 통제권은 우리 Renderer가 가져야 한다.


==================================================
11. Text Element 모델
==================================================

화면에 보여줄 수 있는 텍스트를 의미 단위로 정의한다.

예:

TARGET_WORD
PHONEME
BLEND_SEQUENCE
QUESTION
ANSWER
CAPTION
EXPLANATION
KEY_POINT

각 text element에는 최소:

element_id
role
text
source
emphasis
reveal_policy

를 고려한다.

단 upstream에 없는 화면 문구를 마음대로 창작하지 않는다.

필요한 텍스트가 없으면 MISSING/UNRESOLVED로 기록한다.


==================================================
12. Audio Element 모델
==================================================

Generated Asset을 정확히 참조해야 한다.

각 audio element:

asset_id
source_speech_asset_id
generation_unit_id
speech_mode
file_path
duration_ms
voice_name

가능하면 checksum도 lineage 용도로 포함한다.

중요:

logical Speech Asset과 실제 Generation Unit을 혼동하지 않는다.

KO_NARRATION segmentation이 적용된 경우
SP001과 SP001-1/SP001-2/...를 구분해야 한다.

Render Specification은 실제 재생 파일 단위인 Generation Unit을 알아야 한다.


==================================================
13. Segmented narration ordering
==================================================

SP001-1
SP001-2
SP001-3
SP001-4

같은 segmented narration은:

segment_index
segment_count

를 이용해 정확한 순서를 보존한다.

파일 이름 lexical sort에 의존하지 않는다.

segment lineage가 불완전하면 조용히 추정하지 말고 fail/unresolved 처리한다.


==================================================
14. PAUSE 모델
==================================================

CB06의 3000ms PAUSE를 반드시 Render Specification까지 보존한다.

예:

{
  "type": "PAUSE",
  "duration_ms": 3000,
  "purpose": "VIEWER_ATTEMPT",
  "answer_reveal_allowed": false
}

정확한 필드명은 구현자가 결정 가능.

핵심은:

3초 생각 시간이 사라지면 안 된다.

PAUSE 동안 정답이 먼저 노출되어서도 안 된다.


==================================================
15. Mini Success / Answer Reveal
==================================================

현재 파이프라인에서 이미 보존된:

viewer_must_attempt_before_answer

또는 동등한 production intent를 Render Specification에서도 보존한다.

Mini Success scene에는 최소:

viewer_action
attempt_required
answer_reveal_policy
pause requirement
answer asset/text lineage

가 있어야 한다.

13-1은 실제 frame timing을 계산하지 않지만

"정답은 attempt/pause 이전에 공개하면 안 된다"

라는 의미적 constraint를 명시해야 한다.


==================================================
16. BAG / BAT / MAP / CAP 데이터로 실제 검증
==================================================

Plan 7의 실제 교육 흐름을 조사해서
Render Specification이 최소 다음을 표현할 수 있는지 확인한다.

BAG
/b/
/æ/
/g/
blending

BAT
/t/
blending

MAP
/m/
/p/
blending

CAP
Mini Success / answer reveal

하드코딩하지 않는다.

실제 production_blocks / speech_assets / generated_assets lineage에서 도출한다.


==================================================
17. Generated Asset selection
==================================================

13 Renderer가 과거 실험 variant를 잘못 선택해서는 안 된다.

예:

CAP DIRECT_WORD = REGENERATE_REQUIRED

CAP CONTEXTUAL_WORD = active approved fallback

따라서 Render Specification은 현재 Full Generation Plan / canonical active selection과 동일한 asset을 사용해야 한다.

금지:

generated_assets의 최신 row를 무조건 선택

파일명이 비슷하다고 선택

experimental variant 자동 선택

LOWERCASE_WORD 자동 선택

MINIMAL_CONTEXT_WORD 자동 선택

CONTEXT_RESTRICTED 자동 선택

현재 active 정책을 그대로 소비한다.


==================================================
18. Source of Truth
==================================================

13-1에서 새로운 콘텐츠 판단 엔진을 만들지 않는다.

다음 upstream 결과를 우선 사용한다.

Production Plan
Production Blocks
Speech Assets
Generated Assets
Full Generation Plan
persistent Rendering Readiness
manifest

13-1은 "컴파일러"다.

기존 의미를 다시 추론하거나 재작성하는 단계가 아니다.


==================================================
19. Render Spec Validation
==================================================

Render Specification 생성 후 별도 validation을 수행한다.

최소 확인:

1. canonical rendering readiness = YES
2. 모든 scene이 content_block lineage를 가짐
3. 모든 audio reference가 실제 AVAILABLE/REUSED asset을 가리킴
4. 모든 generation_unit file_path가 존재
5. duration_ms > 0
6. segmented narration ordering 완전
7. source_speech_asset lineage 완전
8. active strategy selection 일치
9. failed/rejected variant 사용 없음
10. experimental variant 자동 선택 없음
11. PAUSE 3000ms 보존
12. viewer_action 보존
13. answer reveal constraint 보존
14. Mini Success lineage 보존
15. Production Block 누락 없음
16. orphan scene 없음
17. 동일 Generation Unit의 의도치 않은 중복 사용 없음

실제 필요에 따라 추가 가능.
