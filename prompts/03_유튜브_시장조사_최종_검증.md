현재 GitHub 프로젝트의 YouTube Market Research 시스템에 대해
"수정 작업"이 아니라 "최종 검증"만 수행해줘.

중요:
- 아직 커밋하지 마라.
- 불필요한 코드 수정 금지.
- 먼저 현재 상태를 검증하고 결과를 보고하라.
- 실제로 문제가 발견된 경우에만 어떤 수정이 필요한지 제안하라.
- 임의로 리팩터링하지 마라.
- 검증 결과는 추측이 아니라 코드, 테스트, 실제 실행 결과를 근거로 작성하라.


==================================================
검증 목표
==================================================

이번 검증의 목적은 최근 개선한 YouTube 시장조사 시스템이
실제로 다음 운영 단계로 넘어갈 만큼 신뢰할 수 있는지 확인하는 것이다.

전체 운영 흐름:

시청자 조사
→ 주제 후보 여러 개
→ 클릭 이유 확인
→ 제목/썸네일 먼저
→ 영상 제작
→ 데이터
→ 다음 주제 결정

현재는 "시청자 조사 시스템" 단계의 최종 검증이다.


==================================================
1. 코드 구조 검증
==================================================

먼저 아래 파일과 관련 흐름을 확인해라.

- data/keyword_pool.yaml
- research/keyword_pool.py
- research/youtube_search.py
- research/db.py
- research/my_channel.py
- research/content_pattern_analyzer.py
- research/weekly_report.py
- research/cli.py
- config/research_config.yaml
- 관련 tests/*

검증할 것:

1. search query가 정확한 problem_id/problem_label에 연결되는지

2. video_keyword_matches가 source of truth 역할을 하는지

3. 한 영상이 여러 problem/search query에 매치될 수 있는지

4. market evidence 부족을 0점으로 처리하지 않는지

5. category별 Outlier가 독립 계산되는지

6. title archetype이 고정 taxonomy로 집계되는지

7. 이번 주 발견과 Evergreen이 discovery timestamp 기준으로 분리되는지

8. CLI 구버전/신버전이 모두 지원되는지


==================================================
2. CLI 하위 호환 검증
==================================================

research keywords add 명령을 확인한다.

새 방식:

--category
--problem-id
--problem-label
--query

가 정상 동작해야 한다.

동시에 기존 방식:

--category
--problem
--query

도 정상 동작해야 한다.

반드시 테스트하거나 안전한 임시 파일/임시 DB를 사용해서 검증한다.

검증 결과:

- 구버전 CLI: PASS / FAIL
- 신버전 CLI: PASS / FAIL

실패한다면 정확한 원인을 적는다.


==================================================
3. Viewer Problem / Matched Query 다중 표시 검증
==================================================

Weekly Report의 개별 Outlier 영상 출력이
videos.problem_category / matched_keyword 단일값에 의존하지 않고

video_keyword_matches의 실제 관계를 사용하고 있는지 확인한다.

다음 테스트 케이스를 반드시 검증한다.


CASE A

하나의 video:
- problem A
- problem B

에 동시에 match

기대:

Viewer problems:
- problem A
- problem B


CASE B

하나의 video가 같은 problem A에

- query 1
- query 2

로 match

기대:

Viewer problems:
- problem A

Matched search queries:
- query 1
- query 2

즉 problem은 중복 출력되지 않고 query는 둘 다 출력되어야 한다.


CASE C

단일 problem + 단일 query 영상

기존처럼 정상 출력되어야 한다.


그리고 다음 모든 섹션에서 같은 방식이 적용되는지 확인한다.

- 이번 주 발견 Outlier
- Evergreen Benchmark
- Category TOP


==================================================
4. market evidence 검증
==================================================

다음 두 경우를 실제 테스트한다.


CASE A: 후보 부족

candidate_video_count < min_candidate_videos

기대:

market_evidence_status = insufficient_data
market_demand_score = null
content_opportunity_score = null


CASE B: 후보 충분

candidate_video_count >= min_candidate_videos

기대:

market_evidence_status = sufficient
market_demand_score 계산
content_opportunity_score 계산


중요:

"데이터 없음"이
"시장수요 0"
으로 표현되면 FAIL이다.


==================================================
5. 카테고리별 TOP 검증
==================================================

다음 category 각각이 독립적으로 TOP 결과를 가질 수 있는지 확인한다.

- reading
- listening
- beginner
- pronunciation
- speaking
- vocabulary

Global TOP에 포함되지 않은 category 영상도
해당 Category TOP에는 정상적으로 나타나야 한다.

테스트 결과를 category별로 PASS/FAIL로 표시한다.


==================================================
6. Title Archetype 검증
==================================================

현재 고정 taxonomy를 확인한다.

최소 다음 개념들이 존재하는지 확인:

- problem_reason
- beginner_target
- one_solution
- result_promise
- roadmap
- time_saving
- contrarian
- number_list
- curiosity_gap
- social_proof
- other

Gemini가 자유로운 이름을 생성해도
최종 집계는 위 taxonomy에 제한되는지 확인한다.

Gemini unavailable 상황에서도 fallback archetype이 동작하는지 확인한다.


==================================================
7. 이번 주 발견 vs Evergreen 검증
==================================================

discovery timestamp를 이용한 필터가 실제 동작하는지 확인한다.

현재 프로젝트가 first_seen_at을 사용하는 경우
불필요하게 새 first_discovered_at 컬럼을 추가하지 않아도 된다.

다음 시나리오를 테스트한다.

- 오래전에 발견된 고점수 영상 A
- 이번 주 처음 발견된 낮은 점수 영상 B

기대:

이번 주 발견 TOP:
B 포함
A 제외

Evergreen:
A와 B 모두 후보


==================================================
8. Viewer Problem 빈도 검증
==================================================

"반복적으로 나타나는 Viewer Problems" 집계가

unique video × problem

기준인지 확인한다.

같은 영상이 같은 problem에 query 2개로 match돼도
1회만 세야 한다.

같은 영상이 서로 다른 problem 2개에 match되면
각 problem에 1회씩 들어가야 한다.


==================================================
9. 전체 자동 테스트 실행
==================================================

전체 테스트를 실제로 실행한다.

가능하면:

pytest -q

또는 현재 프로젝트에 맞는 전체 테스트 명령을 사용한다.

반드시 다음 결과를 보고한다.

- 총 테스트 수
- PASS 수
- FAIL 수
- SKIP 수

실패가 있다면:

- test 이름
- 실패 이유
- 최근 개선 기능과 관련 있는지

를 적는다.

중요:

"테스트 파일이 존재한다"가 아니라
실제 테스트 실행 결과를 보고해야 한다.


==================================================
10. 소량 실데이터 검증
==================================================

전체 6개 category를 바로 대량 실행하지 말고
먼저 reading category 하나만 소량 실데이터로 검증한다.

기존 search cache를 존중한다.

API quota를 과도하게 쓰지 않는다.

가능하면:

- query 수 제한
또는
- 이미 캐시된 데이터 재사용

방식으로 진행한다.


실행 흐름은 현재 CLI에 맞춰 다음 개념을 검증하면 된다.

reading search
→ analyze
→ topic score / patterns
→ weekly report


검증 항목:

- search가 성공하는가
- video_keyword_matches가 저장되는가
- baseline/outlier 계산이 성공하는가
- category TOP이 생성되는가
- Viewer problems가 올바르게 표시되는가
- matched queries가 올바르게 표시되는가
- market evidence 상태가 올바른가
- Weekly Report가 정상 생성되는가


==================================================
11. API quota 검증
==================================================

이번 검증 실행에서 사용한 YouTube Data API quota를 확인한다.

보고:

- 예상 quota
- 실제 quota
- search.list 호출 수
- cache hit 여부

비정상적으로 quota가 증가하면 원인을 설명한다.


==================================================
12. Weekly Report 눈검증
==================================================

생성된 실제 Weekly Report를 직접 읽고 다음을 확인한다.

1. 같은 영상의 여러 Viewer Problem이 모두 보이는가

2. 동일 problem이 중복 출력되지 않는가

3. 여러 search query가 모두 보이는가

4. 데이터 부족 category가 0점으로 오해되지 않는가

5. Category TOP이 독립적으로 존재하는가

6. 이번 주 발견 / Evergreen이 구분되는가

7. 제목 archetype 반복 빈도가 정상적으로 묶이는가

8. 추천 TOP5가 evidence를 포함하는가

9. 사람이 읽었을 때 "왜 이 주제가 추천됐는지" 이해 가능한가
