현재 GitHub 프로젝트의 YouTube Market Research 시스템을 개선해줘.

중요:
- 기존 프로젝트 구조를 최대한 유지한다.
- 이미 잘 작동하는 YouTube API 수집, channel baseline, outlier detector,
  opportunity score 로직은 특별한 이유가 없으면 변경하지 않는다.
- 먼저 현재 코드를 읽고 구조와 데이터 흐름을 이해한 뒤 수정한다.
- 추측해서 새 시스템을 만들지 말고 현재 구현을 기반으로 수정한다.
- 기존 테스트가 있다면 유지하고, 변경사항에 대한 테스트를 추가한다.
- API quota를 불필요하게 증가시키지 않는다.
- 수정 후 어떤 문제가 있었고 무엇을 어떻게 고쳤는지 보고한다.


==================================================
목표
==================================================

현재 시스템을 단순한 "Outlier 영상 찾기"에서

시청자 고민 조사
→ 시장에서 검증된 주제 후보 발견
→ 클릭 이유/제목 패턴 발견
→ 내 채널에 맞는 콘텐츠 후보 생성

까지 신뢰할 수 있는 시장조사 시스템으로 개선한다.


==================================================
문제 1. Viewer Problem 분류 오류
==================================================

현재 research/keyword_pool.py에서 category의 problems 중 첫 번째 problem을
primary_problem으로 선택하고 같은 category의 모든 search query에 동일한
problem을 연결하는 구조가 있다.

이 때문에 실제로 서로 다른 시청자 고민으로 검색된 영상도
모두 같은 Viewer problem으로 표시될 수 있다.

예:
beginner category에 여러 고민이 있어도

"읽기부터 해야 하는가 회화부터 해야 하는가"

하나로 대부분 표시되는 문제가 발생할 수 있다.

이를 수정해라.


[원하는 구조]

keyword pool을 가능하면 아래 개념으로 변경한다.

category
  → problems
      → problem_id
      → label
      → search_queries

예:

reading:
  problems:
    - id: cannot_read_words
      label: "알파벳은 아는데 영어 단어를 못 읽는다"
      search_queries:
        - "영어 단어 읽는 법"
        - "처음 보는 영어 단어 읽기"

    - id: stress_problem
      label: "영어 단어의 강세 위치를 모르겠다"
      search_queries:
        - "영어 강세"
        - "영어 단어 강세"


각 search query는 반드시 자신이 어떤 viewer problem에서 나온 검색어인지
추적할 수 있어야 한다.

영상에는 최소한 다음 정보가 추적 가능해야 한다.

- matched category
- matched problem_id
- matched problem label
- matched search query

하나의 영상이 여러 검색어/문제에 걸릴 수 있으므로 기존
video_keyword_matches 구조를 활용하거나 확장해서
multiple matches를 보존한다.

videos.problem_category 하나만으로 모든 정보를 대표하게 만들지 않는다.

기존 DB와 최대한 호환되도록 migration 전략을 고려한다.


==================================================
문제 2. "데이터 없음"을 "시장수요 0"으로 처리하는 문제
==================================================

현재 research/my_channel.py의 topic score 계산에서
관련 market evidence가 없으면 market_demand_score가 0이 될 수 있다.

하지만:

시장수요 0

과

아직 조사 데이터가 충분하지 않음

은 전혀 다른 의미다.

이를 구분해라.


[원하는 결과]

각 category/topic에 다음 상태를 추가한다.

market_evidence_status:
- sufficient
- insufficient_data

가능하면 다음도 제공한다.

- candidate_video_count
- outlier_video_count
- confidence

confidence 예:
- high
- medium
- low

최소 표본 기준을 config에서 조정 가능하게 한다.

예:

topic_score:
  min_candidate_videos: 10


candidate_video_count < min_candidate_videos이면

market_demand_score를 0으로 확정하지 말고
null 또는 별도의 insufficient 상태로 처리한다.

Weekly Report에서도

reading: 시장수요 0

이라고 표시하지 말고

reading: 데이터 부족 (후보 4개)

처럼 표시한다.


==================================================
문제 3. 모든 핵심 카테고리를 조사
==================================================

현재 schedule을 확인하고 다음 핵심 category가 모두
정기적으로 조사되는지 확인해라.

- beginner
- reading
- listening
- pronunciation
- speaking
- vocabulary

현재 schedule에서 빠진 category가 있다면 추가한다.

단, YouTube Data API quota를 고려해야 한다.

현재 search.list는 비용이 높으므로:

- 기존 search cache 유지
- 같은 query 중복 검색 금지
- 하루 예상 quota 계산 가능하게 유지
- 필요하면 카테고리를 요일별로 분산

한다.

합리적인 기본 schedule을 만들어라.

예:

Monday: reading
Tuesday: listening
Wednesday: beginner
Thursday: pronunciation
Friday: speaking
Saturday: vocabulary
Sunday: report

단 현재 CLI/자동화 구조와 충돌한다면
기존 구조에 가장 자연스럽게 맞는 방식으로 구현한다.

==================================================
문제 5. 제목 패턴 분석을 고정 Archetype으로 변경
==================================================

현재 Gemini가 title_pattern을 자유서술하기 때문에
거의 모든 영상이 서로 다른 패턴 이름을 만들어
Weekly Report에서 각각 1건으로 집계되는 문제가 있다.

자유서술형 title_pattern을 그대로 집계하지 말고
고정된 archetype taxonomy를 만든다.


기본 archetype 후보:

1. problem_reason
   문제 + 이유

2. beginner_target
   왕초보/연령/특정 수준 타깃

3. one_solution
   이것 하나면 끝 / 핵심 하나

4. result_promise
   원하는 결과 약속

5. roadmap
   단계/순서/로드맵

6. time_saving
   시간 절약/빠른 결과

7. contrarian
   기존 상식 반박/하지 마세요

8. number_list
   숫자/몇 가지 방법

9. curiosity_gap
   왜 그런지 궁금증 유발

10. social_proof
    조회수/성공 사례/다른 사람의 검증


Gemini에게는 위 taxonomy에서

primary_archetype 1개
secondary_archetype 최대 1개

만 선택하게 한다.

필요하면 "other"를 허용한다.

그리고 기존 rule-based flags는 유지한다.


Weekly Report에서는:

- one_solution: 8건
- result_promise: 6건
- beginner_target: 5건
- problem_reason: 4건

처럼 실제 반복 빈도가 보이도록 한다.


==================================================
문제 6. "이번 주" 기간 필터 수정
==================================================

현재 weekly_report.py는 보고서 상단에는

기간: start_date ~ end_date

를 표시하지만 Outlier SQL 조회에서 실제 날짜 필터가 없는지 확인해라.

만약 없다면 현재 "이번 주 TOP"은 DB 전체 TOP일 가능성이 있다.

이를 수정한다.


단 여기서 두 개를 구분해야 한다.

A. 이번 주에 새로 발견된 시장 Outlier
B. 장기적으로 계속 강한 Evergreen Outlier


Weekly Report에는 가능하면 두 섹션으로 나눈다.


## 이번 주 발견 Outlier TOP 10

이번 조사 기간에 새로 수집/발견된 영상 기준.


## Evergreen Benchmark TOP 10

DB 전체에서 여전히 참고 가치가 높은 강력한 Outlier.


단순 published_at만으로 "이번 주 영상"을 판단하지 않는다.

오래된 영상이라도 이번 주 검색 과정에서 처음 발견됐다면
시장 벤치마크로 가치가 있기 때문이다.

따라서 가능하면 DB에:

first_discovered_at

또는 이에 해당하는 discovery timestamp를 사용한다.

기존 DB에 없으면 안전한 migration을 추가한다.


==================================================
문제 7. Viewer Problem 빈도도 실제 match 기준으로 계산
==================================================

Weekly Report의

"반복적으로 나타나는 시청자 고민"

은 videos.problem_category 단일 필드만 세지 말고
새롭게 개선된 problem match 데이터를 기반으로 계산한다.

같은 영상이 여러 query에 잡혀 중복 과대계산되지 않도록 한다.

기본 집계 단위는:

unique video × viewer problem

으로 한다.


예:

알파벳은 아는데 단어를 못 읽는다 — 12개 영상
아는 단어인데 원어민 발음이 안 들린다 — 9개 영상
영어 강세 위치를 모르겠다 — 7개 영상
처음 보는 단어를 어떻게 읽어야 할지 모르겠다 — 6개 영상


이 형태가 되어야 한다.

==================================================
중요한 설계 원칙
==================================================

1. 기존 Outlier 계산 공식을 이유 없이 변경하지 않는다.

2. channel baseline 계산 구조를 이유 없이 변경하지 않는다.

3. YouTube API quota 사용량을 크게 늘리지 않는다.

4. 기존 search cache를 유지한다.

5. Gemini는 분류/해석에 사용하고,
   조회수/Outlier/시장점수 같은 숫자는 코드로 계산한다.

6. LLM이 경쟁 영상 제목을 그대로 복사하지 않게 한다.

7. 데이터가 없으면 "0"이라고 판단하지 않는다.

8. 모든 추천에는 evidence가 있어야 한다.

9. 추천 시스템보다 먼저 조사 데이터의 신뢰도를 높인다.

10. 기존 CLI 명령이 깨지지 않도록 backward compatibility를 최대한 유지한다.


==================================================
테스트
==================================================

변경 후 테스트를 추가/수정해라.

최소 다음 케이스를 테스트한다.

1. 같은 category 안의 서로 다른 search query가
   서로 다른 viewer problem으로 저장되는지

2. 하나의 video가 여러 problem에 match될 수 있는지

3. 데이터 부족 category가 market demand 0으로 나오지 않는지

4. category TOP5가 각각 독립적으로 생성되는지

5. title archetype이 고정 taxonomy로 집계되는지

6. weekly report의 "이번 주" 데이터가 discovery period를
   실제로 반영하는지

7. 동일 video/problem 중복 match가 viewer problem 빈도를
   부풀리지 않는지

8. 기존 주요 테스트가 모두 통과하는지
