# 5. 매우 중요한 기존 사실

13-4C-10에서 Typography Scale 비교를 위해 사용한 reference weight는:

DOMINANT 800
PRIMARY 700
SUPPORTING 500
CAPTION 400
MICRO 400

이었다.

그러나 이것들은:

APPROVED FONT WEIGHTS가 아니다.

오직 Typography Scale Review를 위한
preview/reference 값이었다.

또한 기존 조사에서 Verdana 800은:

`browser-synthesized (no true 800 face)`

상태로 보고되었다.

즉:

Verdana에 실제 native 800 face가 있다는 것을
검증한 적이 없다.

이번 단계에서 이를 숨기거나
"800 native verified"라고 표현하면 안 된다.


# 6. 먼저 실제 Font Weight 환경을 조사하라

후보 숫자를 만들기 전에 다음을 조사하라.

- visual_design.py의 typography 관련 구조
- 기존 CANDIDATES
- role style definitions
- `_parse_role_style`
- 13-4C-3 Font Family Review
- 13-4C-10 Typography Scale Review
- 현재 CSS weight 사용처
- generated prototype의 실제 weight
- scene_visual_rules
- phase override
- QUESTION / ANSWER_CONFIRMATION / CASE_BRIDGE
- caption / supporting / micro 사용처
- 실제 renderer가 아직 존재하지 않는지
- font-weight가 현재 어떤 consumer에서 사용되는지

그리고 다음 질문에 답할 수 있어야 한다.

1. 현재 800/700/500/400/400은 어디에서 왔는가?
2. 이것이 canonical value인가, preview reference인가?
3. Verdana에서 브라우저가 실제로 어떤 weight를 합성할 가능성이 있는가?
4. 한국어 fallback인 Malgun Gothic에서는 동일 weight가 어떻게 처리될 수 있는가?
5. Font Weight 변경이 현재 어느 semantic role에 영향을 주는가?
6. font_weight category를 승인하면 향후 renderer가 어떤 값을 소비해야 하는가?

브라우저 또는 OS 내부 font file을 실제로 검사하지 않았다면
native face 존재 여부를 추측하지 마라.


# 7. Font Weight 후보 설계 원칙

후보는 3개를 만든다.

단, 아래 후보 이름은 semantic label이며,
실제 숫자는 current code와 기존 reference를 조사한 뒤
합리적으로 결정하라.

후보:

A = LIGHTER_HIERARCHY

B = BALANCED_HIERARCHY

C = STRONG_BEGINNER


## 후보 설계 목적

### A — LIGHTER_HIERARCHY

- 화면 압박감 감소
- 긴 학습 콘텐츠에서 피로도 감소
- 계층 구조는 유지
- 지나치게 얇아 초보자 가독성이 떨어지지 않아야 함


### B — BALANCED_HIERARCHY

현재 13-4C-10에서 사용했던 reference:

800 / 700 / 500 / 400 / 400

을 baseline 후보로 우선 검토한다.

실제 코드 조사 결과 이것이 현재 reference와 정확히 일치한다면
B는 그 값을 그대로 사용해도 된다.

단:

"현재 값이니까 승인값"이라고 해석하면 안 된다.


### C — STRONG_BEGINNER

- 왕초보 학습자의 핵심 단어 인지성 강화
- DOMINANT / PRIMARY를 더 강하게 구분
- SUPPORTING / CAPTION / MICRO는 과도하게 굵어지지 않도록 제한
- 모든 텍스트를 bold로 만드는 방식 금지


# 8. 숫자를 임의로 발명하지 마라

중요하다.

후보 weight를 단순히:

700/600/400...
800/700/500...
900/800/600...

처럼 이유 없이 만드는 것을 금지한다.

반드시 다음 근거를 남겨라.

- current reference weight
- semantic role
- hierarchy
- browser synthesis 가능성
- Verdana/fallback behavior
- beginner readability
- 기존 prototype과의 비교 가능성

가능하면 deterministic transformation rule을 사용하라.

예:

baseline에서 role별 한 단계 낮춤/유지/높임

등.

단 실제 프로젝트 구조에 맞는 규칙을 먼저 조사하라.


# 9. CSS weight 현실성 검증

후보를 만들 때 다음을 확인하라.

CSS font-weight 값은 유효해야 한다.

그리고:

- 400
- 500
- 600
- 700
- 800

등을 사용한다고 해서
해당 font file의 native face가 존재한다고 주장하면 안 된다.

브라우저가 synthetic bold/interpolation/fallback behavior를
사용할 수 있다는 사실을 Review 화면에 명시하라.

특히 Verdana 800에 대해서는 기존 unresolved fact를 보존한다.

# 11. hierarchy validation

각 후보에서 최소한 다음 semantic hierarchy를 검증하라.

DOMINANT >= PRIMARY >= SUPPORTING >= CAPTION

MICRO는 metadata 역할이므로
CAPTION보다 강해지지 않아야 한다.

단순 숫자 ordering만으로 충분하지 않다면
semantic validation을 추가하라.

예:

DOMINANT weight >= PRIMARY weight
PRIMARY weight >= SUPPORTING weight
SUPPORTING weight >= CAPTION weight
MICRO weight <= CAPTION weight

실제 후보 설계가 이 규칙과 충돌한다면
왜 그런지 명시하고 임의로 통과시키지 마라.

CASE T
DB write detected → fail

CASE U
approved_visual_profile mutation → fail

CASE V
previous review artifact mutation → fail

CASE W
non-deterministic candidate generation → fail


# 29. Determinism

동일 input state에서:

build_font_weight_candidates(...)

결과는 항상 동일해야 한다.

prototype의 semantic content도 동일해야 한다.

파일 timestamp 등 비본질 metadata를 제외하고
후보 정의 자체는 deterministic해야 한다.
