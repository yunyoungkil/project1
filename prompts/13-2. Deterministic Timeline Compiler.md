# 13-2. Deterministic Timeline Compiler

## 목적

13-1에서 생성한 Renderer-neutral Render Specification을 입력으로 받아,
실제 렌더러가 사용할 수 있는 결정론적 시간축(Deterministic Timeline)을 생성한다.

이번 단계의 핵심 질문은 하나다.

"13-1에서 확정된 Scene / Audio / PAUSE / Answer Reveal 순서를 실제 시간축의 start_ms / end_ms로 어떻게 배치할 것인가?"

13-2는 디자인 단계가 아니다.

이번 단계에서는:
- Remotion을 선택하지 않는다.
- React를 사용하지 않는다.
- HTML/CSS를 만들지 않는다.
- FFmpeg filter를 만들지 않는다.
- 화면 디자인을 결정하지 않는다.
- 폰트/색상/위치/애니메이션을 결정하지 않는다.
- 영상 생성 AI를 호출하지 않는다.
- Gemini TTS를 호출하지 않는다.
- 새로운 WAV를 생성하지 않는다.
- Production Plan을 수정하지 않는다.
- Render Specification의 의미를 변경하지 않는다.

오직 시간축만 컴파일한다.

- segmented narration은 Generation Unit 순서가 보존되어 있다.

==================================================
1. 가장 중요한 설계 원칙
==================================================

13-2는 시간을 임의로 창작하면 안 된다.

시간 계산의 authoritative source는 가능한 한 다음으로 제한한다.

1. audio_elements[].duration_ms
2. pause_requirements[].duration_ms
3. 13-1에서 보존된 event/list order
4. Scene 순서
5. 명시적으로 존재하는 reveal constraint

다음과 같은 값을 임의로 넣지 않는다.

예:

- "설명 후 500ms 쉬자"
- "단어를 1초 보여주자"
- "장면 전환에 300ms 넣자"
- "화면을 보기 좋게 2초 유지하자"
- "정답 공개 전에 700ms 기다리자"

이런 것은 13-2 책임이 아니다.

필요하다면 unresolved timing requirement로 남기거나
후속 visual/layout/motion 단계의 책임으로 넘긴다.


==================================================
2. Canonical Timebase
==================================================

Timeline의 canonical timebase는 milliseconds로 한다.

예:

{
  "start_ms": 1200,
  "end_ms": 2840,
  "duration_ms": 1640
}

이번 단계에서 FPS를 임의 확정하지 않는다.

13-1의:

- width = null
- height = null
- fps = null
- orientation = null
- resolution_policy = UNRESOLVED_NON_BLOCKING

정책을 그대로 존중한다.

따라서 frame number를 canonical source로 사용하지 않는다.

향후 FPS가 결정되면:

frame = time_ms * fps / 1000

방식으로 파생할 수 있다.

만약 frame 관련 필드를 추가한다면 반드시:

DERIVED_ONLY_WHEN_FPS_RESOLVED

성격이어야 한다.

FPS가 null인 상태에서 임의로 30fps를 가정하지 않는다.


==================================================
3. 입력 Gate
==================================================

13-2는 아무 Render Spec이나 Timeline으로 변환하면 안 된다.

반드시 최신 Render Specification을 읽고 다음을 확인한다.

최소 조건:

- spec_version == "13.1"
- production_plan_id 존재
- rendering_readiness.ready == true
- scenes 존재
- unresolved critical fields == 0
- 13-1 validation PASS
- Ready for Timeline Compilation == YES

가능하면 DB 최신 render_specs 행을 source-of-truth로 사용하되,
13-1에서 생성된 JSON 파일과 의미가 일치해야 한다.

둘 사이 불일치가 발견되면 임의 선택하지 말고 FAIL 처리한다.


==================================================
4. Timeline Compiler Architecture
==================================================

권장 구조:

latest Render Specification
        ↓
validate_timeline_entry_gate()
        ↓
compile_scene_events()
        ↓
compile_scene_timeline()
        ↓
compile_global_timeline()
        ↓
validate_timeline()
        ↓
run_timeline_integrity_check()
        ↓
ready_for_scene_layout_gate()
        ↓
save DB / JSON / report

함수명은 기존 프로젝트 naming convention을 조사한 뒤
더 적합한 이름이 있으면 조정 가능하다.

단, 책임 분리는 유지한다.


==================================================
5. Source Speech Asset와 Generation Unit을 다시 계산하지 말 것
==================================================

중요하다.

13-2에서:

- TTS strategy selection을 다시 하지 않는다.
- EN_NATIVE fallback을 다시 판정하지 않는다.
- segmentation을 다시 하지 않는다.
- cache를 다시 판정하지 않는다.
- generated_assets를 임의 선택하지 않는다.

13-1 Render Spec에 이미 존재하는:

audio_elements[]

를 사용한다.

13-2는 13-1의 의미를 소비하는 downstream compiler다.


==================================================
6. Event Model
==================================================

각 Scene을 실제 시간 이벤트들의 순서로 컴파일한다.

최소 event taxonomy를 설계하라.

후보:

AUDIO
PAUSE
ANSWER_REVEAL_BARRIER
VIEWER_ACTION
VISUAL_CUE

단, 실제 시간이 필요한 event와
constraint/marker 성격의 event를 구분해야 한다.

AUDIO:
- 실제 duration 있음
- timeline cursor를 전진시킴

PAUSE:
- 실제 duration 있음
- timeline cursor를 전진시킴

ANSWER_REVEAL_BARRIER:
- constraint/marker
- 자체 duration을 임의 생성하지 않음

VIEWER_ACTION:
- 의미 marker일 수 있음
- source에 duration이 없다면 임의 duration 생성 금지

VISUAL_CUE:
- 시간축 marker로 표현 가능
- 별도 hold duration을 임의 생성 금지

taxonomy는 실제 13-1 데이터 구조를 먼저 조사한 뒤 확정한다.

불필요한 event type을 과잉 생성하지 않는다.


==================================================
7. Audio Event
==================================================

각 audio_element는 Timeline에서 실제 Audio Event가 되어야 한다.

최소 필드 후보:

{
  "event_id": "...",
  "event_type": "AUDIO",
  "scene_id": "...",
  "content_block_id": "...",
  "asset_id": "...",
  "source_speech_asset_id": "...",
  "generation_unit_id": "...",
  "speech_mode": "...",
  "file_path": "...",
  "start_ms": 0,
  "end_ms": 1200,
  "duration_ms": 1200
}

필요한 lineage는 보존한다.

특히:

- asset_id
- source_speech_asset_id
- generation_unit_id
- scene_id
- content_block_id

를 잃지 않는다.


==================================================
8. Segmented Narration
==================================================

13-1에서 이미 segmented narration이 Generation Unit 단위로 펼쳐져 있다.

예:

SP001-1
SP001-2
SP001-3
SP001-4

13-2에서는 이 순서를 그대로 사용한다.

절대:

- 문자열 lexical sort
- asset_id 단순 알파벳 sort
- DB row id sort

로 순서를 새로 추론하지 않는다.

13-1이 보존한:

- segment_index
- segment_count
- event/list order

를 authoritative하게 사용한다.

Timeline에서 기본적으로:

SP001-1 end
=
SP001-2 start

이어야 한다.

source에 gap이 명시되어 있지 않으면 임의 gap을 추가하지 않는다.


==================================================
9. Scene Timeline
==================================================

각 Scene은 최소 다음 timeline 정보를 가져야 한다.

{
  "scene_id": "...",
  "content_block_id": "...",
  "scene_role": "...",
  "visual_intent": "...",
  "start_ms": ...,
  "end_ms": ...,
  "duration_ms": ...,
  "events": [...]
}

기본 원칙:

scene.start_ms = 첫 timed event의 start_ms
scene.end_ms = 마지막 timed event의 end_ms
scene.duration_ms = scene.end_ms - scene.start_ms

단, source에 명시된 PAUSE가 있다면 반드시 포함한다.

Scene 사이에 임의 transition gap을 넣지 않는다.

기본적으로:

scene[n].end_ms == scene[n+1].start_ms

이어야 한다.

명시적 gap source가 있는 경우에만 예외 허용.


==================================================
10. Global Timeline
==================================================

8개 Scene을 순서대로 연결해 전체 Timeline을 생성한다.

예:

Scene 1
0 ---------------- 12,400

Scene 2
12,400 ----------- 28,200

Scene 3
28,200 ----------- 41,600

...

최종:

video_duration_ms = 마지막 Scene end_ms

이어야 한다.

Timeline 시작은 기본적으로 0ms로 한다.

negative timestamp는 절대 허용하지 않는다.


==================================================
11. PAUSE 3000ms — CRITICAL
==================================================

Plan 7의 Mini Success CB06에 존재하는:

PAUSE 3000ms

는 절대 변경하면 안 된다.

Timeline에서 실제 timed event로 존재해야 한다.

예:

{
  "event_type": "PAUSE",
  "duration_ms": 3000,
  "start_ms": 12340,
  "end_ms": 15340,
  "answer_reveal_allowed": false
}

반드시:

end_ms - start_ms == 3000

이어야 한다.

2999 / 3001 등으로 변하면 안 된다.

FPS가 아직 없기 때문에 frame rounding 문제도 이번 단계에는 없다.


==================================================
12. Mini Success Answer Reveal Barrier — CRITICAL
==================================================

CB06의 핵심 교육 UX:

질문
↓
학습자가 직접 생각
↓
PAUSE 3000ms
↓
정답 공개
↓
CAP audio

이 순서를 보존한다.

특히 ANSWER text element 또는 answer audio가
PAUSE 종료 전에 reveal 가능한 Timeline 구조가 되어서는 안 된다.

최소 invariant:

answer_reveal_time_ms >= pause.end_ms

정답 audio가 존재한다면:

answer_audio.start_ms >= pause.end_ms

이어야 한다.

answer_reveal_time_ms < pause.end_ms

이면 Integrity FAIL.

단, text element 자체에 아직 실제 visual timestamp를 줄 근거가 없다면
임의로 duration을 만들지 말고:

{
  "reveal_not_before_ms": 15340
}

같은 constraint로 표현하는 방식을 우선 검토한다.

즉:

visual timing을 발명하지 않고 barrier를 시간축에 고정해야 한다.


==================================================
13. Viewer Action
==================================================

CB06의 viewer_action:

viewer_must_attempt_before_answer

의 의미가 Timeline에서도 보존되어야 한다.

viewer_action에 source duration이 없다면
별도 1초/2초 같은 시간을 생성하지 않는다.

대신 PAUSE 및 reveal barrier와 연결한다.

예:

{
  "viewer_action": "...",
  "active_before_ms": 15340,
  "answer_reveal_not_before_ms": 15340
}

실제 필드명은 기존 schema 스타일에 맞게 결정한다.


==================================================
14. Text Elements
==================================================

13-1의:

- TARGET_WORD
- PHONEME
- BLEND_SEQUENCE
- CAPTION
- EXPLANATION
- QUESTION
- ANSWER

를 유지한다.

하지만 13-2에서 모든 Text Element에 임의의 표시 시간을 부여하지 않는다.

두 종류를 구분한다.

A. Timing-resolved text

source event와 명확하게 연결되어 timing을 결정할 수 있는 경우.

B. Timing-constrained / unresolved text

예:

{
  "role": "ANSWER",
  "reveal_not_before_ms": 15340,
  "display_duration_ms": null
}

즉 13-2는:

"언제부터 보여줄 수 있는가"

는 계산할 수 있어도:

"몇 초 동안 보여줄 것인가"

를 임의로 결정하면 안 된다.


==================================================
15. Audio Overlap 정책
==================================================

현재 Production Plan/Render Spec에 audio overlap을 명시하는 구조가 없다면
기본적으로 sequential playback으로 컴파일한다.

즉:

audio[n].end_ms == audio[n+1].start_ms

단, 실제 source에서 overlap intent가 명시되어 있다면 그 의미를 보존한다.

13-2에서 음악/BGM/효과음을 임의로 overlap시키지 않는다.


==================================================
16. Scene Duration 결정
==================================================

Scene duration은 임의 목표 길이가 아니다.

반드시 timed events로부터 파생한다.

기본:

scene_duration_ms
=
sum(sequential audio duration)
+
sum(explicit pause duration)

현재 구조에서 다른 authoritative timed event가 발견되면 포함 가능.

그러나 다음은 포함 금지:

- arbitrary visual hold
- arbitrary transition
- arbitrary padding
- aesthetic delay


==================================================
17. Determinism
==================================================

동일 Render Spec을 두 번 컴파일하면
동일 Timeline이 나와야 한다.

최소 보장:

same render_spec
→ same event order
→ same start_ms
→ same end_ms
→ same scene duration
→ same video duration

created_at 같은 metadata를 제외하고
timeline semantic content가 동일해야 한다.

가능하면 canonical hash/checksum도 검토하라.

단, 실제 필요성이 없다면 과잉 설계하지 않는다.


==================================================
18. Timeline Validation
==================================================

최소 validation:

[Structural]

- Scene 8개 존재
- Scene ID 중복 없음
- Event ID 중복 없음
- duration_ms >= 0
- end_ms >= start_ms
- timed event overlap 없음(명시적 overlap intent 없는 경우)
- Scene overlap 없음
- negative timestamp 없음

[Audio lineage]

모든 Audio Event가 13-1의 audio_element와 정확히 연결되어야 한다.

[Duration]

audio_event.duration_ms
==
source audio_element.duration_ms

[Segmentation]

segment 순서 보존.

[PAUSE]

CB06 PAUSE 정확히 3000ms.

[Answer Reveal]

정답이 PAUSE 종료 전 공개되지 않음.

[Viewer Action]

viewer_action 의미 보존.

[Global Duration]

video_duration_ms
==
last_scene.end_ms

event_order 기반 audio_elements 리스트 순서

- pause_requirements 위치

- viewer_action
- content_intent
- scene_role

QUESTION
→ PAUSE 3000ms
→ ANSWER

순서를 13-1 데이터만으로 확실하게 복원할 수 있어야 한다.

중요:

만약 PAUSE가 pause_requirements[]라는 별도 배열에만 있고
audio_elements 사이의 정확한 삽입 위치를 구조적으로 알 수 없다면,
임의로 추측해서 Timeline을 만들지 않는다.

이 경우:

EVENT_ORDER_AMBIGUOUS

같은 critical unresolved issue로 처리한다.

그리고 13-1 계약을 최소 수정해야 하는지 먼저 보고한다.

이 사전 검증은 13-2의 가장 중요한 항목이다.

QUESTION → PAUSE → ANSWER 순서를 데이터에서 증명할 수 없는 상태에서
Timeline 구현을 진행하지 않는다.
