==================================================
1. BAG를 '백'으로 표기하는 문제
==================================================

현재 실제 산출물에 다음 표현이 존재한다.

Section 3:

B(/ㅂ/) + A(/애/) + G(/ㄱ/)가 빠르게 만나면
'백(BAG)'이 된다.

그리고:

ㅂ + 애 + ㄱ = 백 (BAG)

Section 7:

BAG(백)

Shorts 1:

B(/ㅂ/) + A(/애/) + G(/ㄱ/) = 백(BAG)


이 표현을 수정한다.


문제:

영어 BAG의 마지막 소리는 /g/이고
BACK의 마지막 소리는 /k/이다.

BAG를 단순히 한국어 '백'으로 고정 표기하면
왕초보 학습자가 G와 K의 종성 차이를 잘못 이해할 위험이 있다.


수정 원칙:

BAG의 핵심 설명은

B /b/
+
A /æ/
+
G /g/
→ BAG

처럼 영어 음소 조합을 기준으로 한다.


한국어 표기는 보조 설명일 뿐
영어 발음을 완전히 동일하게 나타내는 표기로 취급하지 않는다.


특히:

BAG = 백

처럼 /g/와 /k/의 차이를 지워버리는
확정적 표기는 사용하지 않는다.


필요하다면 초보자 설명에서는:

"BAG의 마지막은 /g/ 소리입니다."

처럼 명시한다.


==================================================
2. BAT의 '배트/뱃' 이중 표기 문제
==================================================

현재 Section 4:

BAT(배트/뱃)

처럼 두 개의 한국어 표기가 동시에 나온다.


이번 영상의 핵심 목적은
한국어로 영어 발음을 완벽하게 표기하는 것이 아니다.

핵심은:

B /b/
+
A /æ/
+
T /t/
→ BAT

이라는 sound blending 원리를 이해시키는 것이다.


따라서:

BAT(배트/뱃)

처럼 서로 다른 한국어 표기를 동시에 제시하여
왕초보를 혼란스럽게 하지 않는다.


영어 음소 조합을 source of truth로 사용하고,
한국어 발음 표기는 필요한 경우에만 보조적으로 사용한다.


==================================================
3. 'C의 소리는 ㅋ' 일반화 문제
==================================================

현재 Section 6:

"C의 소리는 'ㅋ', A는 '애', P는 'ㅍ'이므로..."

라고 되어 있다.


이 표현은 범위가 너무 넓다.

C는 모든 단어에서 /k/ 소리만 내는 것이 아니다.


하지만 이번 영상에서는
C의 전체 발음 규칙을 설명할 필요도 없다.


따라서 현재 영상에서는:

"CAP에서는 C가 /k/ 소리를 냅니다."

또는 이에 준하는 범위 제한 표현을 사용한다.


금지:

"C는 ㅋ 소리입니다."

처럼 모든 C에 적용되는 일반 규칙처럼 설명하는 것.


이번 영상의 Scope OUT에 해당하는
C의 다른 발음 규칙까지 확장 설명하지 마라.


핵심은 CAP이라는 현재 예시 안에서만
필요한 소리를 알려주는 것이다.

4. Viewer Contract의 약속이 너무 큰 문제
==================================================

현재 Expected Transformation:

"글자 이름을 읊는 대신 글자 소리를 떠올려
처음 보는 단모음 3글자 단어를
망설임 없이 읽을 수 있게 된다."


하지만 현재 Learning Objective와 Scope는:

단모음 A 중심

이며 실제 예시도:

BAG
BAT
MAP
CAP

으로 모두 A 중심이다.


따라서 현재 Expected Transformation은
영상에서 실제로 가르치는 범위보다 넓다.


수정:

Expected Transformation은
현재 영상의 실제 범위와 일치해야 한다.


예:

"글자 이름을 읊는 대신 글자 소리를 떠올려,
단모음 A가 들어간 기초 3글자 단어를
소리 조합으로 읽어볼 수 있게 된다."


핵심:

"모든 단모음 3글자 단어"
또는
"처음 보는 단어를 망설임 없이 읽는다"

수준까지 보장하지 않는다.

6. 한국어 발음 표기의 역할을 명확하게 할 것
==================================================

이번 수정에서 중요한 설계 원칙을 추가한다.


영어 교육 Blueprint에서:

IPA/영어 음소
=
발음 정확성의 기준


한국어 발음 표기
=
왕초보 이해를 돕는 보조 수단


으로 취급한다.


한국어 표기가 영어의 중요한 음소 차이를
왜곡하거나 제거하는 경우에는
한국어 표기를 강제로 만들지 않는다.


특히 다음과 같은 차이를 주의한다.

- /g/ vs /k/
- /b/ vs /p/
- /d/ vs /t/


이번 수정 때문에
IPA 전체를 가르치는 영상으로 바꾸지는 않는다.

IPA는 내부 정확성 및 필요한 최소 표기에 사용하고,
시청자에게 발음기호 암기를 요구하지 않는다.

8. Promise Scope 검증 강화
==================================================

현재 자동 검증은
제목/썸네일과 Core Answer의 관계는 확인하지만,

Viewer Contract의 Expected Transformation이
Learning Objective / Scope보다 넓은지는
충분히 잡지 못했다.


이를 검증한다.


최소한:

Video Promise
Expected Transformation

이

Learning Objectives
Scope IN

보다 과도하게 넓지 않은지 확인한다.


필요하면 Integrity Check에:

promise_matches_scope

를 추가한다.


예:

Scope:
단모음 A CVC

Expected Transformation:
모든 단모음 CVC를 읽는다

→ warning 또는 fail


Scope:
단모음 A CVC

Expected Transformation:
단모음 A가 들어간 기초 CVC를 읽어본다

→ pass

9. CAP의 exception_risk 재검토
==================================================

현재:

CAP
difficulty=medium
exception_risk=medium

으로 되어 있다.


왜 exception_risk=medium인지
코드/생성 로직을 확인한다.


CAP 자체가 이번에 가르치는:

C /k/
A /æ/
P /p/

조합의 예시로 부적절해서 medium인 것인지,

아니면 C가 다른 환경에서는 다른 소리를 낼 수 있기 때문에
medium으로 판단한 것인지 구분한다.


후자라면:

CAP 자체는 현재 예시 안에서는 정상적인 규칙 예시이므로
이를 "예외 단어"처럼 취급하면 안 된다.


단:

임의로 low로 바꾸지 말고
현재 exception_risk 정의와 판정 로직을 먼저 확인하고
필요한 경우 최소 수정한다.
