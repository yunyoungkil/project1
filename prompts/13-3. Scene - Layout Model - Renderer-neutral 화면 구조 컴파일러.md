# 13-3. Scene / Layout Model — Renderer-neutral 화면 구조 컴파일러

## 0. 이번 단계의 목적

13-2까지 우리는 다음을 확정했다.

- 13-1 Render Specification
  - 무엇을 보여줄 것인가
- 13-2 Timeline Compiler
  - 언제 보여줄 것인가

이번 13-3의 책임은 다음 하나다.

> 각 Scene에서 어떤 시각 요소를 화면의 어떤 논리적 영역(Zone)에 배치해야 하는지를 Renderer-neutral 구조로 컴파일한다.

즉:

Production Plan
→ Verified Assets
→ Render Spec
→ Timeline
→ Scene / Layout Model

로 이어지는 구조다.

이번 단계에서는 실제 디자인을 만들지 않는다.

다음 항목은 아직 확정하지 않는다.

- 실제 색상
- 실제 폰트
- font-size px
- 실제 x/y pixel 좌표
- CSS
- HTML
- React
- Remotion
- Motion Canvas
- FFmpeg filter
- easing
- transition animation
- 실제 MP4
- AI 영상 생성

13-3은 "화면 구조"만 정의한다.

핵심 원칙:

> WHAT은 13-1이 결정했다.
> WHEN은 13-2가 결정했다.
> WHERE는 13-3이 결정한다.
> HOW IT LOOKS는 이후 단계가 결정한다.

---

# 1. 절대 원칙

## 1-1. Timeline이 시간축의 유일한 Source of Truth

13-3은 반드시 13-2 Timeline Compiler의 결과를 입력으로 사용한다.

우선 입력:

assets/generated/plan_<ID>/render/timeline.json

또는 DB:

render_timelines의 해당 Production Plan 최신 timeline_json

13-3에서 Render Spec 또는 Production Plan을 다시 해석하여 별도의 timing을 만들지 마라.

특히 다음 값을 재계산하거나 변경하지 마라.

- scene.start_ms
- scene.end_ms
- scene.duration_ms
- AUDIO start/end/duration
- PAUSE start/end/duration
- ANSWER_REVEAL_BARRIER
- VIEWER_ACTION timing
- VISUAL_CUE timing
- video.duration_ms

13-2 Timeline이 canonical timing source다.

# 2. Entry Gate

13-3 실행 전에 반드시 13-2 결과가 Scene/Layout 단계에 진입 가능한지 확인한다.

가능하면 13-2가 이미 제공하는:

ready_for_scene_layout

또는 이에 대응하는 canonical helper/result를 그대로 사용한다.

새로운 독립 Gate 의미를 만들지 마라.

다음이 충족되지 않으면 Layout Model을 생성하지 않는다.

- timeline_version == "13.2"
- Production Plan ID 일치
- Ready for Scene/Layout == YES
- timeline validation PASS
- critical timing unresolved 없음

실패 시 정확한 blocker를 보고한다.

# 3. 이번 단계에서 만들어야 할 핵심 구조

신규 모듈 후보:

research/scene_layout.py

필요한 경우 DB:

scene_layouts

CREATE TABLE IF NOT EXISTS scene_layouts (

단, 기존 DB 패턴을 먼저 조사하고 프로젝트 관례에 맞춰라.

불필요한 테이블/추상화는 만들지 마라.

# 5. Scene Layout의 핵심 개념

각 Timeline Scene에 대해 하나의 Scene Layout을 생성한다.

기본 구조 예:

{
  "scene_id": "...",
  "content_block_id": "CB04",
  "scene_role": "BLENDING",
  "visual_intent": "BUILD_SEQUENCE",
  "start_ms": 126880,
  "end_ms": 181720,
  "duration_ms": 54840,
  "layout_type": "BLENDING_LAYOUT",
  "zones": [...],
  "element_bindings": [...],
  "visibility_rules": [...],
  "layout_constraints": [...]
}

중요:

Timeline timing은 그대로 복사/참조할 뿐 수정하지 않는다.

# 6. Layout Type Taxonomy

최소한 다음 Layout Type을 검토하라.

- OPENING_LAYOUT
- EXPLANATION_LAYOUT
- WORD_FOCUS_LAYOUT
- PHONEME_LAYOUT
- BLENDING_LAYOUT
- PRACTICE_LAYOUT
- MINI_SUCCESS_LAYOUT
- RECAP_LAYOUT
- RESOLUTION_LAYOUT
- UNRESOLVED_LAYOUT

단순히 Scene Role 이름을 기계적으로 복사하지 말고 13-1의:

- scene_role
- visual_intent
- text_elements
- emphasis_targets
- viewer_action
- attempt_required
- answer_reveal_policy

그리고 13-2 Timeline event 구조를 사용해 결정하라.

그러나 임의의 "예쁜 화면" 판단을 넣지 마라.

Layout Type은 화면 구조를 표현하기 위한 semantic classification이어야 한다.

# 7. Zone Model

화면을 실제 pixel 좌표가 아니라 논리적 Zone으로 표현한다.

후보 taxonomy:

- HEADER
- CONTEXT
- MAIN
- PRIMARY_FOCUS
- SECONDARY
- PHONEME
- BUILD_SEQUENCE
- CAPTION
- EXPLANATION
- PROMPT
- ANSWER
- FOOTER

모든 Scene에 모든 Zone이 있을 필요는 없다.

예:

BLENDING_LAYOUT:

- PRIMARY_FOCUS
- PHONEME
- BUILD_SEQUENCE
- CAPTION

MINI_SUCCESS_LAYOUT:

- PROMPT
- PRIMARY_FOCUS
- ANSWER
- CAPTION

EXPLANATION_LAYOUT:

- CONTEXT
- MAIN
- CAPTION

필요하면 taxonomy를 조정할 수 있지만 이유를 보고하라.

---

# 8. Pixel 좌표 금지

13-3에서는 다음처럼 만들지 마라.

BAD:

{
  "x": 620,
  "y": 300,
  "width": 800,
  "height": 400
}

대신 논리적 구조를 사용한다.

예:

{
  "zone_id": "primary_focus",
  "zone_role": "PRIMARY_FOCUS",
  "priority": 100,
  "alignment_intent": "CENTER",
  "size_intent": "DOMINANT"
}

허용 가능한 semantic layout property 예:

- alignment_intent
- size_intent
- priority
- stacking_order
- relationship
- anchor_zone
- max_simultaneous_elements

아직 px/%/CSS grid 값으로 확정하지 않는다.

---

# 9. Element Binding

13-1 Render Spec의 text element와 13-2 event를 Layout Zone에 연결한다.

예:

{
  "element_id": "...",
  "source_element_id": "...",
  "element_role": "TARGET_WORD",
  "zone_id": "primary_focus",
  "priority": 100
}

가능한 element role:

13-1 taxonomy를 그대로 재사용:

- TARGET_WORD
- PHONEME
- BLEND_SEQUENCE
- CAPTION
- EXPLANATION
- QUESTION
- ANSWER

새로운 text role taxonomy를 중복 생성하지 마라.

필요한 경우 visual-only element를 별도 구분할 수 있다.

예:

- PROGRESS_INDICATOR
- EMPHASIS_MARKER
- SEPARATOR

그러나 실제 필요성이 확인된 경우에만 추가한다.

---

# 10. Audio와 Layout 관계

AUDIO Event 자체를 화면 요소로 착각하지 마라.

Audio는 timing driver다.

필요한 경우 audio event와 visual binding의 관계를 기록할 수 있다.

예:

{
  "trigger_event_id": "...",
  "visible_element_ids": [...]
}

하지만 오디오가 존재한다고 자동으로 자막을 만들어내지 마라.

13-1에 정의된 text_elements와 visual intent가 근거다.

---

# 11. Visibility Model

13-3에서 중요한 책임 중 하나다.

어떤 요소가 언제 "보일 수 있는가"를 Timeline constraint와 연결한다.

단, 새로운 arbitrary timestamp를 발명하지 마라.

Timeline event의 timing을 기준으로 한다.

예:

{
  "element_id": "answer_cap",
  "visibility": {
    "policy": "AFTER_BARRIER",
    "barrier_event_type": "ANSWER_REVEAL_BARRIER"
  }
}

또는:

{
  "element_id": "...",
  "visibility": {
    "policy": "SCENE_DEFAULT"
  }
}

가능한 semantic visibility policy 후보:

- SCENE_DEFAULT
- AUDIO_ACTIVE
- AFTER_EVENT
- BEFORE_EVENT
- AFTER_BARRIER
- HIDDEN_UNTIL_REVEAL
- PERSIST_UNTIL_SCENE_END

필요 이상으로 복잡하게 만들지 마라.

# 12. Mini Success는 가장 중요한 검증 대상

Plan 7 CB06 Mini Success를 실제 데이터로 검증한다.

13-2 기준:

CB06:
start = 231560
end = 244600

PAUSE:
240280 → 243280
duration = 3000ms

answer_reveal_not_before_ms:
243280

CAP answer audio:
SP039::CONTEXTUAL_WORD
start = 243280

13-3에서 반드시 보존해야 한다.

Mini Success 화면 구조는 최소한:

PROMPT
PRIMARY_FOCUS
ANSWER

를 구분해야 한다.

ANSWER는 pause 전 노출되어서는 안 된다.

즉:

Question / Prompt
→ Viewer Attempt
→ 3000ms Pause
→ Answer Reveal
→ CAP answer

구조가 Layout Model에서도 깨지면 안 된다.

다음과 같은 constraint가 필요하다.

{
  "element_role": "ANSWER",
  "visibility": {
    "policy": "AFTER_BARRIER",
    "not_before_ms": 243280
  }
}

단, 243280을 새로 계산하지 말고 Timeline의 ANSWER_REVEAL_BARRIER에서 가져와라.

# 13. Viewer Action 보존

CB06 viewer_action을 반드시 보존한다.

Production Plan을 다시 읽어서 새로 해석하지 말고 Timeline/13-1 lineage를 통해 전달된 canonical 값을 사용한다.

viewer_action은 layout에서 다음과 같은 의미를 가질 수 있다.

- prompt zone 필요
- answer zone 분리 필요
- answer pre-reveal 금지

그러나 viewer_action 문구 자체를 변경하지 마라.

# 17. Phoneme Layout

isolated phoneme demo에서는 다음 관계를 표현할 수 있어야 한다.

TARGET WORD 또는 context
→ PHONEME FOCUS
→ 설명/보조 caption

/t/
/m/
/p/
/b/
/g/
/æ/

같은 음소가 화면의 PRIMARY 또는 PHONEME zone에 들어갈 수 있어야 한다.

같은 Charon voice인지 여부 등 음성 정책은 12단계 책임이며 여기서 다시 판단하지 않는다.

# 18. Blending Layout

Plan 7의 중요한 교육 화면이다.

예:

/b/
+
/æ/
+
/g/

→ BAG

또는 의미상:

PHONEME components
→ BUILD_SEQUENCE
→ TARGET_WORD

이 관계를 Layout Model로 표현해야 한다.

실제 화살표 디자인, animation path 등은 아직 결정하지 않는다.

필요한 것은 관계다.

예:

{
  "relationship": "BUILDS_TO",
  "source_zone": "build_sequence",
  "target_zone": "primary_focus"
}

DIRECT_SEQUENCE가 12단계에서 확정된 음성 전략이라는 사실은 유지하되, 13-3에서 음성 전략을 재판단하지 않는다.

# 19. Practice Layout

PRACTICE는 viewer가 먼저 처리해야 하는 정보와 설명 정보를 구분한다.

예:

PROMPT
PRIMARY_FOCUS
CAPTION

필요한 경우 ANSWER를 별도 Zone으로 둔다.

단, answer reveal constraint가 실제 upstream에 있을 때만 적용한다.

모든 Practice에 Mini Success 규칙을 임의 적용하지 마라.

# 20. Recap Layout

RECAP은 이미 배운 요소를 다시 보여주는 Scene이다.

동일 Generation Unit이나 text element가 이전 Scene에서 재사용되는 것은 오류가 아니다.

13-1/13-2에서 확인된 정상적인 재사용을 13-3에서 중복 오류로 오판하지 마라.

Recap에서는 여러 핵심 요소를 병렬로 보여줄 수 있도록 semantic grouping을 지원한다.

예:

{
  "group_role": "RECAP_SET",
  "member_element_ids": [...]
}

필요성이 없다면 group abstraction을 과도하게 만들지 마라.

# 22. Element Priority

Scene 안에서 무엇이 가장 중요한지를 숫자 또는 enum으로 표현할 수 있다.

예:

PRIMARY = 100
SECONDARY = 70
SUPPORT = 40

또는 enum:

PRIMARY
SECONDARY
SUPPORT

프로젝트에 더 단순한 방식을 선택하라.

중요:

priority는 z-index나 font-size가 아니다.

시각적 중요도 semantic이다.

# 23. Simultaneous Visibility

왕초보 교육 화면에서 너무 많은 요소를 동시에 보여주는 문제를 이후 디자인 단계에서 제어할 수 있도록, 13-3에서 구조적 힌트를 제공할 수 있다.

예:

{
  "max_simultaneous_primary_elements": 1
}

또는 Zone별:

{
  "max_simultaneous_elements": 2
}

그러나 임의 숫자를 확정해야 할 근거가 없다면 unresolved non-critical로 남겨라.

"초보니까 무조건 3개" 같은 규칙을 발명하지 마라.

# 24. Emphasis Target 보존

13-1의 emphasis_targets를 버리지 마라.

하지만 실제 강조 방법은 아직 결정하지 않는다.

금지:

- 빨간색
- 확대 130%
- bounce
- glow

허용:

{

}

또는 upstream 값을 그대로 전달.

# 29. Determinism

동일 timeline.json을 두 번 컴파일하면 동일한 Scene/Layout JSON이 나와야 한다.

현재 시간, random, API 결과 등에 의존하지 않는다.

created_at 같은 metadata는 determinism 비교 대상에서 명확히 제외하거나 기존 프로젝트 패턴을 따르라.

---

# 30. Validation

최소 다음을 검증한다.

1. timeline_version == 13.2
2. scene 수 보존
3. scene_id 보존
4. content_block_id lineage 보존
5. scene timing 보존
6. element lineage 보존
7. audio/event lineage 훼손 없음
8. 모든 required visual element가 정확히 하나의 적절한 Zone에 binding
9. unknown critical layout type 없음
10. Mini Success ANSWER가 pause/barrier 이전 노출되지 않음
11. viewer_action 보존
12. PAUSE 3000ms constraint 보존
13. failed/rejected asset을 새로 끌어오지 않음
14. experimental variant를 새로 선택하지 않음
15. renderer-specific implementation leakage 없음
16. pixel/fps/resolution 발명 없음
17. deterministic
18. unresolved critical fields 정확히 보고

필요하면 실제 구조에 맞춰 추가할 수 있다.
