# 09-1단계: 유튜브 대본 품질 및 Retention 교정

## 목적

현재 09단계 `research/script_writer.py` 구현은 전체 테스트를 통과했고,
실제 대본도 `ready_for_production=YES`까지 정상 생성되었다.

따라서 이번 작업은 09단계를 다시 설계하거나 대규모 리팩터링하는 작업이 아니다.

현재 구조를 최대한 유지하면서 실제 생성된 대본에서 발견된 다음 4가지 문제만 교정한다.

1. Scope를 넘어서는 과도한 일반화 표현
2. 학습 효과를 과장하는 표현
3. 글자 음가를 지나치게 일반화하는 표현
4. Blueprint에 설계된 Retention Device가 실제 narration에 충분히 구현되지 않는 문제

기존 DB 구조, CLI, Blueprint, Example Ladder, 점수 체계,
YouTube API 수집 구조는 불필요하게 변경하지 않는다.

`script_2026-08-17.md`

# 2. 문제 A — Scope 초과 일반화 표현

현재 실제 생성 문장:

"이렇게 소리를 차례대로 엮기만 하면 어떤 단어도 소리 내어 읽을 준비가 됩니다."

문제:

현재 영상은 단모음 a가 포함된 기초 CVC 단어만 다룬다.

그런데 "어떤 단어도"라는 표현은
현재 Scope보다 훨씬 넓은 범위를 약속한다.

기존 `promise_matches_scope`가 Video Promise 수준에서는
이를 잡고 있지만 본문 narration 내부의 일반화까지 충분히 잡지 못했다.


## 수정 요구

Script 생성 프롬프트에 다음 원칙을 추가한다.

본문 narration에서도 현재 Learning Scope를 넘어서는 일반화를 금지한다.

특히 다음 표현을 주의한다.

- 어떤 단어도
- 모든 단어
- 어떤 영어 단어든
- 이제 다 읽을 수 있다
- 이것만 알면 다 읽힌다
- 항상
- 무조건
- 완벽하게

단, 문맥상 명확하게 현재 Scope로 한정되어 있다면 허용할 수 있다.

예:

BAD:
"이 방법이면 어떤 단어도 읽을 수 있습니다."

GOOD:
"이런 기초 3글자 단어는 같은 방식으로 읽어볼 수 있습니다."

GOOD:
"오늘 다룬 단모음 a가 들어간 CVC 단어에서는 같은 원리를 적용해볼 수 있습니다."


# 3. 결정론적 Scope 백스톱 강화

Gemini 프롬프트만 수정하지 말고,
대본 전체 narration을 대상으로 하는 결정론적 Integrity Check를 추가하거나
기존 `no_scope_creep`를 확장한다.

권장 이름:

`narration_scope_safe`

다음과 같은 과잉 일반화 표현을 탐지한다.

- 어떤 단어도
- 모든 단어
- 어떤 영어 단어든
- 다 읽을 수
- 전부 읽을 수
- 무조건 읽
- 완벽하게 읽

단순 문자열 하나만 검사하지 말고
최소한 위 계열의 표현을 안정적으로 탐지할 수 있도록 구현한다.

단, 현재 Scope를 명확히 한정하는 문맥은 false positive가 되지 않도록 한다.

예:

"모든 단어를 읽을 수 있습니다."
→ fail

"오늘 배운 네 단어를 모두 읽을 수 있습니다."
→ pass

"이런 기초 3글자 단어를 읽어볼 수 있습니다."
→ pass


# 4. 문제 B — 학습 효과 과장 표현

현재 실제 생성 문장:

"외우지 않아도 소리가 저절로 연결됩니다."

문제:

Sound Blending은 이해만으로 자동화되는 것이 아니라
실제 반복 연습이 필요한 학습 과정이다.

"저절로 연결된다"는 표현은
학습 효과를 필요 이상으로 확정적으로 표현한다.


## 수정 요구

Script 생성 프롬프트에 다음 원칙을 추가한다.

학습 결과를 자동적·즉각적·보장된 결과처럼 표현하지 않는다.

피해야 할 표현 예:

- 저절로 됩니다
- 바로 됩니다
- 한 번에 됩니다
- 이것만 알면 됩니다
- 자동으로 됩니다
- 무조건 됩니다
- 완벽하게 됩니다

대신 학습 행동 중심으로 표현한다.

예:

BAD:
"외우지 않아도 소리가 저절로 연결됩니다."

GOOD:
"글자 이름을 읊는 대신 각 글자의 소리를 하나씩 연결하는 연습을 해보세요."

GOOD:
"처음에는 천천히 소리를 나눠 말한 뒤 조금씩 이어 붙여보세요."


# 5. 학습 효과 과장 백스톱

기존 `no_false_guarantee`가 위와 같은 표현을 충분히 탐지하는지 먼저 확인한다.

이미 탐지할 수 있다면 새 체크를 만들지 말고 기존 체크를 강화한다.

탐지하지 못한다면 결정론적 검사를 보완한다.

중요:

단순히 "바로"라는 단어 하나가 있다고 fail시키면 안 된다.

예:

"바로 다음 단어를 보겠습니다."
→ pass

"이 원리만 알면 바로 모든 단어가 읽힙니다."
→ fail

즉, 학습 결과를 보장하는 문맥인지 확인하도록 설계한다.


# 6. 문제 C — 글자 음가 일반화

현재 Section 1 실제 문장:

"예를 들어 글자 B는 이름이 '비'이지만, 단어 안에서는 입술을 뗐다 붙이며 내는 /b/ 소리를 냅니다."

문제:

08-1에서 이미 Example Scope 원칙을 추가했지만,
현재 생성된 narration에서는 다시

"B는 단어 안에서 /b/ 소리를 낸다"

형태의 일반화가 발생했다.

현재 영상의 교육 원칙은
글자의 음가를 모든 단어에 대한 절대 규칙처럼 설명하지 않고
현재 예시 안에서 설명하는 것이다.


## 수정 요구

다음과 같은 표현을 피한다.

BAD:
"B는 단어 안에서 /b/ 소리를 냅니다."

BAD:
"C의 소리는 /k/입니다."

대신 현재 예시에 범위를 한정한다.

GOOD:
"BAG와 BAT 같은 오늘의 예시에서는 B가 /b/ 소리를 냅니다."

GOOD:
"이 단어 CAP에서는 C가 /k/ 소리를 냅니다."


# 7. example_scope_safe 강화

현재 `example_scope_safe`가 위 Section 1 문장을 통과시킨 이유를 조사한다.

현재 체크가

"<글자>의 소리는"

같은 특정 문장 패턴만 감지하고 있다면,
다음 형태도 탐지할 수 있도록 최소 확장한다.

예:

"B는 단어 안에서 /b/ 소리를 냅니다."

"C는 /k/ 소리를 냅니다."

"G는 /g/ 소리를 냅니다."

즉,

[알파벳 글자] + 조사 + [IPA] + "소리"

형태의 일반화도 검사한다.

단 다음과 같이 특정 example scope가 있으면 pass:

"이 단어 CAP에서는 C가 /k/ 소리를 냅니다."

"BAG와 BAT에서는 B가 /b/ 소리를 냅니다."

"오늘 예시에서 G는 /g/ 소리를 냅니다."


# 8. 문제 D — Retention Device 실제 narration 반영 부족

현재 Script Score:

- Example Alignment: 100

Script Writer가 이를 실제 narration으로 충분히 변환하지 못하고 있다.


# 9. Retention 설계 원칙

Retention을 올리기 위해 억지로 질문을 많이 넣어서는 안 된다.

다음 목적에 해당할 때만 짧은 참여 장치를 사용한다.

1. 다음 예시를 예측하게 한다.
2. 앞에서 배운 원리를 다시 사용하게 한다.
3. 정답 공개 전에 짧게 생각하게 한다.
4. 다음 Section으로 넘어갈 이유를 만든다.

권장 예:

BAG 완료 후:

"그럼 끝 글자만 바꾸면 어떻게 될까요?"

BAT 완료 후:

"이번에는 앞 글자까지 바꿔보겠습니다. 그래도 같은 방법일까요?"

MAP 진입:

"M-A-P, 제가 읽기 전에 세 소리를 한번 떠올려보세요."

CAP 진입:

"이제 마지막은 여러분 차례입니다."


# 10. Retention 구현 규칙

모든 Section에 질문을 강제로 넣지 않는다.

다만 Blueprint에 다음과 같은 retention device가 존재한다면
Script Writer는 가능한 경우 narration에 실제로 반영해야 한다.

예:

- open_loop
- question
- quiz
- prediction
- contrast
- challenge
- participation

Blueprint의 retention device를 읽고
실제 narration으로 변환했는지 확인한다.

단순히 `?` 개수를 늘려 Retention Score를 올리는 방식은 금지한다.


# 11. Retention Score 개선

현재 Retention Score 계산 방식도 검토한다.

현재 방식이 질문형 문장 개수에 지나치게 의존한다면,
Blueprint retention device가 실제 Script에서 구현됐는지도
보조 신호로 사용할 수 있는지 검토한다.

단:

점수를 높이기 위한 인위적인 계산식 변경은 금지한다.

실제 narration 품질이 개선된 경우에만
Retention Score가 올라가야 한다.

가능하다면 다음 요소를 사용한다.

- prediction prompt
- viewer challenge
- delayed answer
- open loop
- contrast transition
- mini success participation

질문 부호 개수만으로 고득점하지 않도록 한다.

# 16. Retention 목표

현재 Retention Score는 20.5다.

수정 후 특정 숫자를 억지로 맞추지 않는다.

그러나 실제 Blueprint retention device가 narration에 반영되었다면
현재 20.5보다 의미 있게 개선되는 것이 정상이다.

Retention 점수를 올리기 위해

- 의미 없는 질문 추가
- 같은 질문 반복
- 점수 공식 임의 완화
- 임계치 낮추기

등을 하지 않는다.

실제 콘텐츠 개선 → 점수 개선 순서가 되어야 한다.
